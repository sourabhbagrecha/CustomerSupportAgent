# Architecture

The component diagram is in the root [README](../README.md#architecture). This file is the deep dive behind it: what each layer does, and which files own it.

Everything (app data, the action ledger, the event log, and LangGraph's own checkpoints) lives in one SQLite file. There is no second process, queue, cache, or external database.

**Agent loop** (`server/src/agent/graph.ts`): a small three-node LangGraph.js graph, `loadContext` (deterministic: fetches the customer's orders/payments, retrieves relevant past-conversation summaries via FTS5, searches policy) feeding a Zod-schema-bound `agent` node that loops with a `tools` node until it produces a final reply. Model calls go through a thin wrapper (`server/src/agent/modelClient.ts`) with a 30s timeout, retry with backoff+jitter, and failover from `PRIMARY_MODEL` to `FALLBACK_MODEL`; if both are unavailable the server returns a fixed, LLM-free apology and writes an escalation record without ever touching a model client again. The context block `loadContext` assembles now opens with a `current_date` block (the system clock's UTC date) so the model has a deterministic fact to do refund-window arithmetic against instead of guessing, and the system prompt's hard rule 8 forbids opening an eligibility reply with a bare "yes" or "no": the policy verdict (window, cap, prior refunds) has to come first, since a refund outside the window or above the cap is not "eligible," it needs a human exception or review. That failover can cross providers: a model id containing a `/` (OpenRouter's `vendor/model` naming) is routed to OpenRouter's own endpoint and key regardless of `OPENAI_BASE_URL` (`server/src/agent/providerConfig.ts`), so the shipped default genuinely fails over to a different vendor rather than a cheaper model from the same one; each retry attempt is numbered 1-indexed in the trace ("attempt 1", not "attempt 0") alongside the real backoff-plus-jitter wait time it slept. A separate hard rule (6) requires the model to call `get_conversation_history` itself, this turn, before any money action that rests on a customer's claim of a prior agent's promise; a deterministic check in the money pipeline (`promiseEvidenceFoundThisTurn` in `server/src/ledger/pipeline.ts`) blocks the action unless that call actually returned a matching conversation, not merely that a lookup happened, so a fabricated promise cannot move money by pointing at a lookup that found nothing.

**Money path** (`server/src/ledger/pipeline.ts`, `server/src/policy/engine.ts`): `issue_refund`/`issue_credit` are never raw model tools. Every call runs: policy check (against `fixtures/policy.json`, generated from the same source as the human-readable `fixtures/policy.md`) → a ledger row written **before** any external call, keyed by `sha256(threadId + actionType + orderId + amount)` → the mock payment call → reconciliation on timeout (checks `get_payments` for a matching completed payment before ever retrying, and only ever retries once with the same key). A jailbroken model cannot bypass this: the policy engine only looks at order/payment facts and the caps in `policy.json`, never at what the model claims. An escalation that carries its own pending money amount (the above-cap remainder after a policy-capped portion already auto-succeeded, hard rule 6) gets its own new `awaiting_approval` ledger row and its own idempotency key (`createEscalationLedgerRow` in `server/src/ledger/pipeline.ts`), rather than pointing at the already-settled capped row; granting it runs through the exact same idempotent `issue_refund`/`issue_credit` path, recording who authorized it in a new `override_by` column. Once a ledger row carries a human `resolution` (`approved` or `rejected`) it is append-only: `resolveApprovedAction`/`resolveRejectedAction` return the row's existing outcome unchanged rather than re-executing or overwriting `reason` again, so a double-click, a second tab, or a stale escalation reference can never grant the same money twice.

**Observability** (`server/src/events/*`): every step, LLM call, tool call, guardrail verdict, fault, failover, and escalation is written to an `events` table and pushed over SSE to the trace panel, live. This is the whole observability story: there is no external tracing SDK to configure and no account to create (see [decisions.md](decisions.md) for why Langfuse was considered and dropped). Two structured `step` events make what the model actually saw and spent legible rather than inferred: a `context` event, written right after `loadContext` assembles the turn, records the policy version, how many of the customer's past conversations were retrieved against the total corpus, order/payment counts, and the prompt's token budget, tagged with a fresh per-turn `traceId`; a `rollup` event, written when the agent node is about to return control with no further tool calls queued, closes the same turn out with its LLM call count, tokens in/out, an estimated USD cost (priced per model the same way the eval cost figure is), and wall time. The trace panel shows the `traceId` per turn for log correlation, and the chat header sums every `rollup` event in a thread into a running cost/latency badge.

**Audit view** (`web/src/components/AuditPanel.tsx`, `GET /api/approvals/pending`, `GET /api/ledger`): the trace panel is per conversation, so the UI has a second tab that reads across all of them. It lists every item currently waiting on a human, on any thread, and lets an operator resolve it in place; that queue is the only surface where a decision is made, because the chat pane is the customer's side of the conversation and shows a read-only "waiting on a human reviewer" strip instead (`docs/plans/004-decisions-leave-the-customer-chat.md`); below it sits the full `actions_ledger`, filterable by status, so the "a ledger row is written before any money moves" invariant is visible rather than only assertable. Denied and `awaiting_approval` rows appear there too, which is the point: the rows where no money moved are the ones that prove the policy engine ran.

**Evals view** (`web/src/components/evals/`, `server/src/evals/`, routes under `/api/evals`): a third tab is a model-comparison workbench over the run archive in `evals/runs/` (one JSON file per eval run: label, provider base URL, primary/fallback/judge model, git commit, prompt and fixtures sha256, per-scenario status, latency, tokens, and judge notes). It lists every archived run (with a dollar cost per run, see [evaluation.md](evaluation.md)), lets you tick any number of them and compares them (see [evaluation.md](evaluation.md)), and it can start a new run: you pick the base URL (OpenAI, OpenRouter, or any OpenAI-compatible endpoint), the model IDs, which server-side `*_API_KEY` variable to use (by name; the value never leaves the server), optionally a scenario subset, and the judge stays pinned to the server's own judge model unless you override it, so cross-provider runs are graded alike. The server runs the suite as a child process (the same `vitest` invocation `npm run eval` makes), streams progress from the per-scenario artifacts, and writes the run record when it exits; UI-started runs never rewrite `evals/results.json`/`RESULTS.md`, which remain the committed regression-gate snapshot from `npm run eval`. Plans: `docs/plans/007-model-comparison-eval-runs.md`, `docs/plans/009-eval-comparison-visualisation.md`.

**Human decision queue** (`server/src/ledger/approvals.ts`, `server/src/agent/notify.ts`): the same queue holds two kinds of row. A `requires_approval` verdict pauses the LangGraph turn mid-flight via `interrupt()`, exactly as before. An `escalate_to_human` call (policy conflicts, distress, a denial the customer pushed back on, or an above-cap remainder from hard rule 6) also enqueues a row, carrying the actual policy-denial reason and the customer's escalation context, but does not pause anything: the agent's turn already finished; when that escalation is about a specific pending amount it is backed by its own new ledger row (see "Money path" above in this file), never by pointing at a row that already settled. Either way, resolving the row lets an operator grant an exception (replay the row's own idempotency key through the money pipeline, recording the approver in `override_by`, so a denied or escalated amount can still be paid exactly once) or uphold the original decision.

Two separate free-text fields keep a reviewer's private reasoning out of the customer's inbox: an internal note (`ApprovalRow.remark`, audit-only, rendered only in the Audit tab) and a customer-facing note (`ApprovalRow.customerNote`, the only one `notify.ts` ever relays), the latter also passed through a small wordlist profanity backstop before it can reach a transcript. A customer-facing note is required whenever the outcome is a refusal (reject, or uphold a denial). The composed notice and outcome reach the customer as a deterministic, code-composed chat message appended straight to that thread's conversation state, never phrased by a model, so the reviewer's note cannot be reworded, softened, or dropped.

# Evaluation

How the eval suite is built, what the run archive holds, and how the comparison view reads. Current pass/fail numbers live in [`evals/RESULTS.md`](../evals/RESULTS.md), which is regenerated by every `npm run eval` (runs the suite and rewrites the gate files).

## Suite and judge


The suite now spans 22 scenarios: the original 15, four added alongside the ownership-enforcement and fault-injection hardening in `docs/plans/005-hardening-ownership-atomicity-evals.md`, and three more (20 `grant-amount-matches-escalation`, 21 `verified-promise`, 22 `fabricated-promise`) added while responding to an external black-box evaluation report, recorded in `docs/plans/010-eval-report-fixes.md`. Current pass/fail status, latency, and token counts for every scenario live in [`evals/RESULTS.md`](../evals/RESULTS.md), regenerated on every `npm run eval`; that file is the up-to-date source, since this README is not regenerated automatically alongside it. A scenario that errors or is skipped now counts as a failure rather than shrinking the denominator, `npm run evals:gate` (`scripts/evals-gate.ts`) exits non-zero on any scenario that regressed against the stored baseline, and the runner supports `--repeats N` (default 1, no added cost unless opted in) to replay every selected scenario N times at the CLI (`npx tsx scripts/run-eval.ts --repeats 3`, `--repeats` is the flag, `3` is how many times to run each selected scenario); the run-launcher UI does not expose that flag yet.

The reply-quality judge is three-state rather than pass/fail: `scored` (the judge returned a real tone/grounded verdict, which the scenario then hard-asserts on), `unscored` (the judge call itself failed, for example a model error), or not applicable (the scenario never calls the judge, e.g. a pure clarifying-question or fault-recovery case). A judge failure used to fail open silently and count as a pass; that fallback is gone. `evals/RESULTS.md` now marks every unscored row visibly as `UNSCORED (judge unavailable)` instead of hiding it inside a green run, and `evals/results.json` carries a top-level `metadata` block (the primary/fallback model IDs read from env, the git commit, the run count, and sha256 hashes of the system prompt and the fixtures) so a given results file states exactly what it exercised.

Each full run also computes a **judge calibration** figure: the same judge grades a 12-transcript hand-labeled golden set (`evals/goldenSet.ts`) and the run record stores the percentage agreement (`runGoldenSetCalibration` in `evals/judge.ts`), surfaced on the metadata line of `evals/RESULTS.md`. The labels in that golden set were drafted by an AI agent while building this mechanism, not by a human reviewer, and the file says so in its own header; treat the agreement percentage as evidence the mechanism runs and reports something, not as a validated judge-accuracy number, until a human has read and corrected those 12 transcripts.

Scenarios 16 through 19 cover the gaps the ownership and fault-injection hardening opened up: **16** (`16-foreign-order-refund`) has one customer demand a refund on another customer's order and asserts zero succeeded or reconciled ledger rows and zero successful `issue_refund` result; **17** (`17-foreign-data-isolation`) asks for another customer's payment history and profile and asserts none of that customer's PII reaches the reply or the event log; **18** (`18-tool-500-recovery`) and **19** (`19-tool-slow-latency`) inject a `tool_500` and a `tool_slow` fault respectively and assert the turn still completes with no ledger row left stuck pending and recovery visible in the trace. Scenario 15 (`15-malformed-tool-args`) also got stricter: its recovery assertion is event-order based, not presence based, checking that the injected validation failure is followed later in the event stream by either a successful `tool_result` or an `escalation`, because the fault fires before any event is even written for the failed call itself, so a check that only looked for "an error happened somewhere" could never actually fail.

The authoritative per-scenario table (status, latency, tokens, judge notes, and the metadata block described above) is [`evals/RESULTS.md`](../evals/RESULTS.md), regenerated by every `npm run eval` and committed alongside each change so the diff shows quality movement.

**Run archive and model comparison** (`evals/runs/`, plan 007): every eval run, whether started by `npm run eval` or from the Evals tab, also writes one self-describing record to `evals/runs/<timestamp>-<label>.json` (same per-scenario rows as `results.json`, plus the provider block: base URL, primary/fallback/judge model IDs, no keys). The archive is committed, so it accumulates across models and commits instead of being overwritten; the first record is the gpt-5.4-mini baseline converted from the `results.json` at commit `a21ce5f`. The Evals tab reads it (`GET /api/evals/runs`) and renders the side-by-side comparison; `npm run eval` keeps owning `results.json`/`RESULTS.md`, and a UI-started run (or a subset run) only adds a record. To try another provider, either set `OPENAI_BASE_URL`, `PRIMARY_MODEL`, `FALLBACK_MODEL`, and `OPENAI_API_KEY` in `.env` and run `npm run eval`, or use the tab's launcher (`POST /api/evals/runs`), which passes the chosen base URL, model IDs, and the named key variable's value into the child process environment only. Either way the judge resolves from `JUDGE_MODEL` / `JUDGE_BASE_URL` / `JUDGE_API_KEY` (defaulting to `FALLBACK_MODEL` on the agent's own key and endpoint), and the launcher pins it to the server's resolved judge by default, so two runs of different agent models are graded by the same judge model unless you override that on purpose. A subset run is supported (`npx tsx scripts/run-eval.ts 14 18` runs only scenarios 14 and 18; `npx tsx` executes a TypeScript file directly and the numbers are scenario numbers from `evals/scenarios/`) for cheap spot checks; it writes a record flagged with its `scenarioFilter` and never touches the gate snapshot. `scripts/export-results.ts` remains as a recovery tool (`npx tsx scripts/export-results.ts --label <text>` rebuilds a record and the gate files from whatever is left in `evals/.artifacts/`, for a run whose export did not happen).

**Cost per run** (plan 008): each run record also carries a `pricing` block, the USD-per-million-token `prompt` and `completion` rates for the run's primary model, snapshotted when the run started from OpenRouter's public model listing (`GET https://openrouter.ai/api/v1/models`, the data behind [openrouter.ai/models](https://openrouter.ai/models), no key needed; `server/src/evals/pricing.ts`). A model served by OpenRouter is looked up by its id as-is; a model called directly at `api.openai.com` is looked up under OpenRouter's `openai/` prefix with its snapshot date stripped or matched against the listing's canonical slug, and anything ambiguous resolves to no price rather than a guess. The Evals tab multiplies the recorded token counts by those rates to show a Cost column in the runs table, a "Cost (USD)" row with deltas in the comparison, and a per-scenario cost in the matrix; `evals/RESULTS.md` carries the same figure on a metadata line. The number is the agent model's tokens at list price: judge calls are not counted (the judge is the same model on every run by design, so it would add a constant), cache discounts and high-volume tiers are ignored, and a run whose model the listing does not price (or a run made while openrouter.ai was unreachable, the fetch has an 8 second timeout and never fails the run) shows `n/a`. `npx tsx scripts/backfill-pricing.ts` (developer-only; `npx tsx` runs the TypeScript file directly, no arguments) stamps today's price onto archived records that have none and leaves priced ones alone; the three runs archived before this field existed were backfilled that way and the rewritten records committed.

**Prompt versioning** (plan 012): every run record has always carried `promptSha256` (the hash of `server/src/agent/prompt.ts` at run time); the Evals tab now surfaces it as a prompt-version chip, the first 12 characters of that hash in a pill whose color is derived from the hash, so runs of the same prompt version share a color and a prompt change is visible at a glance. The chip appears as a "Prompt" column in the runs table and under the model name on each scorecard and comparison column header, with the full hash in the tooltip, so selecting two runs of the same model across a prompt change compares that prompt change's effect on pass rate, latency, tokens, and cost directly. Behind each hash there is a committed snapshot: at run start the runner copies prompt.ts to `evals/prompts/<first 12 chars of the hash>.txt` if that file does not already exist (content-addressed, so re-running the same prompt writes nothing new), which makes any archived version readable and diffable later, for example `git diff --no-index evals/prompts/<a>.txt evals/prompts/<b>.txt` (compares the two snapshot files directly, outside git history). Runs recorded before this feature existed have a hash but may have no snapshot behind it; the ones whose prompt version matched a committed prompt.ts were backfilled from git history, and hashes from uncommitted working-tree prompts are noted as unrecoverable.

**Reading the comparison** (plan 009): the selected runs are shown three ways, in the order a model choice is actually made. One scorecard per run leads with the pass rate as its headline figure and carries cost, mean latency, and total tokens under it, each with a delta against the baseline card only where both runs have that number; a run that covers fewer scenarios than the widest selected one says so on the card, because 16/16 is not the equal of 19/19. Under that, one scatter plot puts pass rate on the vertical axis and cost (or mean latency, or tokens, switchable) on the horizontal, so up and to the left is better: the runs that no other run beats on both axes are the Pareto frontier, drawn filled and joined by a staircase, and everything else is hollow because something already beats it on both counts. Marker size is mean latency, every dot is labelled, and a run with no value for the chosen axis (an unpriced model, a run with no token counts) is named under the chart as not plotted rather than dropped or parked at zero. Last is the scenario grid: one row per scenario, one cell per run, a status glyph on a status fill, with failures drawn solid and passes pale so a single failure in a column of passes is what the eye lands on. It filters to the scenarios where the selected runs disagree (usually the only rows worth reading once more than two runs are up) or to the scenarios anyone failed, hovering or tab-focusing a cell gives that run's latency, tokens, cost, and judge state, and clicking a row expands the per-run notes and judge notes. The original two tables are still there, collapsed, under "Table view": every number in the three views above is reachable there without hovering. The chart and the grid are hand-written SVG and HTML, no charting library.

Plus 130 deterministic unit tests (`npm run test`, no LLM calls) covering the policy engine (including the credit bound), idempotency key derivation, ledger/reconciliation transitions, ledger and human-decision-queue queries (including the escalation kind and its remark), granting an exception on a denied row, the deterministic customer-notice text, HTTP query-parameter and eval-run request validation, retrieval ranking, `policy.md`/`policy.json` consistency, customer ownership (policy engine, provider adapter, database triggers), approval compare-and-set and execution retry, tool output schema validation, `loadContext` degradation under a transient support-API error, provider/judge resolution and base-URL normalisation, the eval run record (artifact grouping, run ids, schema round trip, the legacy `RESULTS.md` export), and eval-run pricing (mapping a model id and base URL onto OpenRouter's listing, per-token to per-million conversion, the cost arithmetic).
## External evaluation report: fixes and status

An external, black-box evaluation report against a running instance of this app (no source access, testing through the UI and API only) found 12 issues spanning correctness (a money/ledger wiring bug in the escalation flow), missing operational tooling (no demo reset), a real data leak (a reviewer's internal remark reaching the customer), a prompt-injection-adjacent gap (an unverified prior-promise claim could trigger money), a resilience gap (the fallback model came from the same vendor as primary), eval rigor, customer-facing wording, observability (invisible context engineering, no cost rollup), and a handful of UI issues. Six parallel Claude Code subagents fixed the findings in one pass, split by file ownership so each subagent's edits stayed inside its own files; two further repair rounds followed, each gated by a real `npm run eval` run against the live model rather than by inspection alone, because the first full run after the fixes surfaced three real regressions inspection had missed. `docs/plans/010-eval-report-fixes.md` is the full record of that work, including both repair rounds and the final eval outcome.

| Issue | Status |
|---|---|
| Escalating an above-cap remainder pointed at an already-settled ledger row instead of creating its own; a grant could re-execute or overwrite a settled row | Fixed: escalations get their own new `awaiting_approval` row and idempotency key; settled rows are append-only; `override_by` records the approver |
| No way to reset demo data between runs or reviewers | Fixed: `POST /api/demo/reset` plus a header "Reset demo" button with a `window.confirm` step |
| A reviewer's internal remark could reach the customer's chat transcript | Fixed: separate internal (audit-only) and customer-facing note fields, plus a wordlist profanity backstop on the customer-facing one |
| A claimed prior promise could trigger money on the strength of the claim alone | Fixed: hard rule 6 plus a deterministic backstop requiring an actual, matching `get_conversation_history` result this turn, not just that the call happened (the weaker "call happened" check was itself a bug caught during this pass; see eval scenario 22) |
| `FALLBACK_MODEL` defaulted to a model from the same vendor as `PRIMARY_MODEL`, so a vendor-wide outage defeated the failover | Fixed: `FALLBACK_MODEL` can now be an OpenRouter-style id on a different provider, routed correctly regardless of `OPENAI_BASE_URL` |
| Eval suite under-covered judgment calls and could silently shrink its own denominator | Fixed: suite grew 19 to 22 scenarios, `--repeats` support added at the CLI, an errored/skipped scenario now counts as failed, `npm run evals:gate` added, a judge-vs-golden-set calibration figure added |
| A reconciled refund read as internal machinery ("reconciled", "duplicate") to the customer | Fixed: a reconciled result now reads as plain first-time success; "Ledger ID" relabeled "Reference #" in customer-facing text |
| Context engineering (retrieval counts, policy version, token budget) was invisible in the trace | Fixed: a structured `context` step event every turn |
| No visibility into per-turn or per-thread LLM cost/latency | Fixed: a `rollup` step event per turn plus a cumulative cost/latency badge in the chat header |
| UI polish: fault toggles felt broken, judge failures dumped a raw string, no per-turn trace id, an allow-worded string could render under "Denied because", no de-escalation line for unverifiable authority claims | Fixed: per-toggle pending state instead of one shared disable flag (the real bug); judge failures now show assertion name plus plain-word expected/actual; a trace id is shown per turn; a render-time filter guards "Denied because"; a canned de-escalation reply was added for claims like "I am the store manager" |
| The eval judge silently inherited an OpenRouter-style `FALLBACK_MODEL` while still calling the OpenAI base URL, causing judge errors | Fixed: an explicit `JUDGE_MODEL` env var plus independent OpenRouter-aware routing in `evals/judge.ts` |
| Eval scenario 05 (`vague-compensation-clarification`) reply stopped reliably ending in a literal "?" | Documented open item: most likely a side effect of a prompt-wording change made during repair, see [failure-modes.md](failure-modes.md); not fixed this pass |
| Eval scenario 20 (`grant-amount-matches-escalation`) drives the grant step through direct function calls rather than a full model-produced tool-call sequence | Documented open item: a deliberate simplification, noted in the scenario file's own header comment |
